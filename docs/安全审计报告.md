## 二、已修复问题详情

### V1 路径穿越（高危）

**问题**

网关把请求路径直接拼接到上游地址：

```python
upstream = f"{SGLANG_BASE_URL}/v1/{path}"
```

而路由是通配的 `/v1/{path:path}`，`path` 未做任何校验。攻击者用 `curl --path-as-is` 阻止客户端规范化路径，即可越出 `/v1/` 前缀。

**实际验证（修复前）**

```bash
# 读取服务器内部信息
curl --path-as-is "https://域名/v1/../get_server_info" -H "Authorization: Bearer sk-qw-xxx"
# → {"internal":"版本信息、显存占用、模型路径等敏感内容"}   HTTP 200

# 触发管理端点，清空 KV 缓存
curl --path-as-is "https://域名/v1/..%2f..%2fflush_cache" -X POST -H "Authorization: Bearer sk-qw-xxx"
# → {"detail":"缓存已清空"}   HTTP 200
```

**影响**

任何持有合法 Key 的用户（或 Key 泄露后的攻击者）都能：

- 调用 `/flush_cache` 清空 KV 缓存，让所有在线用户性能骤降（拒绝服务）
- 调用 `/get_server_info` 读取版本、显存占用、模型路径
- 触达 SGLang 其他未预期的管理端点

**修复**

新增 `_safe_path()`，改为**白名单**校验，只放行明确的推理端点：

```python
DEFAULT_ALLOWED_PATHS = "chat/completions,completions,embeddings,models,rerank,score"
ALLOWED_PATHS = {p.strip() for p in os.getenv("ALLOWED_PATHS", DEFAULT_ALLOWED_PATHS).split(",") if p.strip()}
```

拦截规则：拒绝 `..`、反斜杠、以 `/` 开头、含 `?` `#` 空字节的路径，并对路径再做一次 URL 解码后复查（防双重编码）。

**回归验证（修复后）**

| 请求 | 结果 |
|---|---|
| `/v1/models` | 200 |
| `/v1/../get_server_info` | 404 |
| `/v1/..%2f..%2fflush_cache` | 404 |
| `/v1/..%252f..%252fflush_cache`（双重编码） | 404 |
| `/v1/internal_dump`（非白名单） | 404 |

### V2 异常信息泄露（中危）

**问题**

```python
except Exception as exc:
    return _error(500, f"网关内部错误：{exc}", "internal_error")
```

把内部异常原样返回给客户端，可能泄露文件路径、依赖库版本、内网地址等。

**修复**

异常详情只写服务端日志，客户端只拿到通用提示：

```python
except Exception:
    logger.exception("网关内部错误")
    return _error(500, "网关内部错误，请稍后重试。", "internal_error")
```

### V3 请求体大小检查时机错误（中危）

**问题**

```python
body = await request.body()          # 先整个读进内存
if len(body) > MAX_BODY_BYTES:       # 然后才检查
    ...
```

攻击者发送一个远超上限的 body，内存会在检查之前就被占满。

**修复**

先看 `Content-Length` 声明值做预检，读取后再复查一次（兜住 chunked 编码等无声明长度的情况）：

```python
declared = request.headers.get("content-length", "")
if declared.isdigit() and int(declared) > MAX_BODY_BYTES:
    return _error(413, "请求体过大。", "payload_too_large")

body = await request.body()
if len(body) > MAX_BODY_BYTES:
    return _error(413, "请求体过大。", "payload_too_large")
```

**验证**：发送 11MB body（上限 10MB）→ 413。

### V4 无输出长度上限（中危）

**问题**

客户端可以传 `max_tokens: 100000`，单次请求长时间独占 GPU，同时烧掉大量 token 配额。配额机制拦不住这种单请求攻击——它只在**请求前**检查已用量。

**修复**

新增 `MAX_OUTPUT_TOKENS`（默认 4096），对 `max_tokens` 和 `max_completion_tokens` 同时钳制：

```python
for field in ("max_tokens", "max_completion_tokens"):
    value = payload.get(field)
    if isinstance(value, int) and value > MAX_OUTPUT_TOKENS:
        payload[field] = MAX_OUTPUT_TOKENS
```

**验证**：发送 `max_tokens: 100000`、`max_completion_tokens: 99999`，上游实际收到的均为 4096（默认上限）；发送 `max_tokens: 100` 时原样透传，不受影响。

**修复**：只返回 `{"status": "ok"}`。

### V6 数据库文件权限（低危）

**问题**：SQLite 文件权限由 umask 决定，默认可能为 644，同机其他账号可读。

库内只存密钥的 SHA-256 哈希（不可逆，且 Key 本身是 256 位随机串，无法暴力破解），所以风险有限，但用量数据包含使用行为。

**修复**：`Store` 初始化时自动把主库及 `-wal`、`-shm` 附属文件收紧到 600。

**验证**：

```
-rw-------  sec2.db
-rw-------  sec2.db-shm
-rw-------  sec2.db-wal
```

### V7 缺少全局并发闸门（中危）

**问题**

`ConcurrencyGuard` 原本只按 Key 计数，没有全局上限。每个 Key 单独看都在限额内，但叠加起来没有任何天花板。

**影响**

50 个用户，每人 `max_concurrent=4`（默认值），峰值就是 **200 路并发同时打到 SGLang**。显存会被 KV Cache 撑爆，所有请求一起变慢甚至 OOM。

值得强调的是：**这不是恶意攻击，正常使用就能触发。** 用户越多越容易踩到。

**修复**

加全局计数，超限返回 429 `service_busy`：

```python
GLOBAL_MAX_CONCURRENT = int(os.getenv("GLOBAL_MAX_CONCURRENT", "32"))
```

`acquire()` 改为返回 `'ok' / 'global_full' / 'key_full'`，两种拒绝给不同的错误码，便于客户端区分是「你自己开太多了」还是「服务整体忙」。

**验证**：单 Key 上限设 10、全局上限设 2，占用 2 路后第 3 路返回 429 `service_busy`；释放后恢复 200。

### V8 鉴权失败不受限流（中危）

**问题**

`_authorize` 的顺序是「先查 Key，再限流」。Key 无效时直接返回 401，**根本走不到限流那一步**。

**影响**

攻击者用垃圾 Key 无限次请求，每次都触发一次 SHA-256 计算加一次 SQLite 查询，却不消耗任何配额。这是一条免费的资源消耗通道，且不会出现在用量统计里。

**修复**

新增 `FailureLimiter`，按客户端 IP 统计鉴权失败次数：

```python
AUTH_FAIL_MAX = int(os.getenv("AUTH_FAIL_MAX", "20"))
```

配套新增 `_client_ip()`，优先读 Cloudflare 注入的 `CF-Connecting-IP`，否则回落到 `request.client.host`。**这一步是必需的**——经过 Tunnel 的所有请求源地址都是 `127.0.0.1`，不读这个头的话限流会退化成全局计数，一个攻击者就能把所有人挡在门外。

**验证**：阈值设 5，前 5 次无效 Key 返回 401，第 6 次起返回 429 `too_many_failed_attempts`。

**已知权衡**：该检查位于所有请求之前（这样才能在数据库查询前就拦掉洪水），因此同一出口 IP 下的正常用户理论上会被牵连。默认阈值 20 次/分钟对正常使用足够宽松；如果用户集中在同一个公司网络或 VPN 出口，可适当调高。

### V9 SQLite 未设 busy_timeout（低危）

**问题**

只设了 `journal_mode=WAL` 和 `synchronous=NORMAL`，没有设 `busy_timeout`。SQLite 该参数默认为 0，遇到锁**立即**抛 `database is locked`。

**影响**

网关与 CLI 同时写入时（比如你一边签发 Key、一边有请求在跑）会报错，请求返回 500。属于偶发、难排查的一类故障。

**修复**

```python
self._conn.execute("PRAGMA busy_timeout=5000")
```

### V10 流式收尾顺序不当（低危，已加固）

**问题**

原来的 `finally` 块把 `await resp.aclose()` 写在最前面：

```python
finally:
    await resp.aclose()          # 可能被取消
    ...
    release_once()               # 上面若抛异常，这里就不执行
```

客户端断连时生成器会被取消，此时 `await` 可能再次抛 `CancelledError`，导致后面的 `release_once()` 被跳过，**并发计数永久泄漏**——该 Key 从此再也发不出请求，只能重启网关。

**验证结果：实测未复现。**

构造了「发起 2 路长流式请求 → 2 秒后强制断开 → 再连续请求 3 次」的场景，3 次均返回 200，计数被正确释放。Python 的取消传播在这一路径上没有触发问题。

**处理**

仍然调整了顺序作为加固——先落定并发位和用量（同步操作，不会被取消打断），再做 `aclose()` 并吞掉异常：

```python
finally:
    try:
        _record(...)
    except Exception:
        logger.exception("记录用量失败")
    finally:
        release_once()

    try:
        await resp.aclose()
    except BaseException:
        pass
```

成本极低，消除了这个理论风险窗口，也让代码意图更明确。

**补充验证（第三轮）**

改用更长的流式响应（20 个分块、约 2 秒）重新测试，在 0.5 秒时强制断开客户端，随后连续请求 3 次**全部返回 200**，并发位被正确释放。数据库里也能查到该请求的审计记录（耗时 502ms，与断连时刻吻合）。V10 的风险确认不存在。

### V11 单实例锁文件被清空（低危）

**问题**

```python
handle = open(path, "w")      # "w" 会立即把文件截断为 0 字节
try:
    fcntl.flock(handle.fileno(), fcntl.LOCK_EX | fcntl.LOCK_NB)
except OSError:
    handle.close()
    raise RuntimeError(...)
```

锁本身基于文件描述符，第二个实例加锁失败**不影响**正在运行的实例。但 `"w"` 模式在加锁**之前**就把文件截断了，于是：

- 正在运行的实例写进去的 PID 被抹掉
- 锁文件变成 0 字节，运维时想确认「现在跑的是哪个进程」就查不到了

实测复现：主实例启动后锁文件内容为 `49444`，在另一端口尝试启动第二个实例，失败后锁文件内容变成空字符串。

**影响**

纯运维可观测性问题，不构成安全漏洞。但会误导排查方向——看到空锁文件容易以为「没有实例在跑」。

**修复**

改用 `"a+"` 模式（存在则不截断），加锁成功后再回绕写 PID：

```python
handle = open(path, "a+")
try:
    fcntl.flock(handle.fileno(), fcntl.LOCK_EX | fcntl.LOCK_NB)
except OSError:
    handle.close()
    raise RuntimeError(...) from None
handle.seek(0)
handle.truncate()
handle.write(str(os.getpid()))
handle.flush()
```

**验证**：主实例 PID 49444 → 第二实例启动失败 → 锁文件内容仍为 `49444`。

### V12 客户端断连未与正常完成区分（低危）

**问题**

流式请求的审计记录一律写 `ok`。客户端中途断连时，上游返回的状态码确实是 200，但从审计角度看，「完整读完」和「读了一半就跑」是两件完全不同的事：

- 客户端程序 bug 导致的反复重连
- 有人在批量抓取部分输出后提前断开

这两种情况在原来的日志里都表现为一堆正常的 `ok`，看不出异常。

**修复**

在 `_stream_and_record` 里区分三种收尾：

```python
if completed:
    outcome = "ok" if status < 400 else "upstream_error"
elif upstream_broken:
    outcome = "stream_broken"
else:
    # 客户端中途断连，状态码记 499（nginx 对「客户端提前关闭连接」的约定）
    outcome = "client_abort"
    status = 499
```

区分手法：客户端断连时生成器被注入的是 `GeneratorExit`，它**不是** `Exception` 的子类，所以 `except Exception` 捕不到它，天然与「上游中断」区分开。

**验证**：完整流式 → `ok` / 200 / 2025ms；0.5 秒断连 → `client_abort` / 499 / 504ms。

顺带确认了一点：断连的请求**照常计费**。拿不到 `usage` 时按字符数兜底估算（该次记为 405 tokens），所以「读一半就断」无法绕过 token 配额。

## 三、已验证为安全的设计

这几处容易被认为是漏洞，但实际是安全的：

| 项目 | 为什么安全 |
|---|---|
| SQL 注入 | 全部使用参数化查询，无字符串拼接用户输入 |
| 密钥存储 | 只存 SHA-256 哈希，且原 Key 是 256 位随机串，不可逆推 |
| Key 泄露后重放 | 可随时 `cli.py revoke` 吊销，比改密码快 |
| CORS 通配符 | 鉴权走 Header 而非 Cookie，浏览器不会自动携带凭证，无法被跨站利用 |
| OPTIONS 免鉴权 | CORS 预检请求按规范本就不携带凭证，不构成绕过 |
| 并发计数泄漏 | 流式与非流式分支都在 `finally` / 异常处理中释放信号量 |
| Tunnel 凭证文件 | 权限已是 `400`；`cert.pem` 为 `600` |
| 客户端断连时的并发计数 | 用 2 秒长流式 + 0.5 秒断连实测，断连后连续 3 次请求均 200，计数正常释放 |
| 客户端断连绕过配额 | 断连请求仍按字符数兜底估算并入库（实测记 405 tokens），配额不会被绕过 |
| 多实例误启动 | 文件锁在 `lifespan` 启动阶段获取，第二个实例直接抛 `RuntimeError` 退出，不会静默让全局并发上限翻倍 |
| 请求头透传 | 只透传 `content-type` 与 `accept`，客户端的 Authorization 不会被带到上游 |
| 上游响应透传 | 只透传 `content-type`，不泄露 `server` 等内部头 |
| 审计日志写入失败 | `AuditContext.finish()` 整体包在 `try/except` 里，审计是旁路，写失败不会影响用户请求 |
| 审计记录重复写入 | `finish()` 用 `written` 标志保证幂等，避免同一请求落多条 |

## 四、残余风险（需人工处理）

### 4.1 限流状态已持久化，但并发计数仍在内存（部分解决）

**原问题**：`SlidingWindowLimiter` 与 `ConcurrencyGuard` 都是进程内状态，重启即重置、多 worker 不共享。

**已解决**：限流状态（每分钟请求数、鉴权失败次数）已迁移到 SQLite 的 `rate_events` 表，重启不再清零。

做过专门验证：把某个 Key 的限流打满后重启网关，重启后的**第一次请求仍然返回 429**，数据库里能看到对应的限流事件记录。以前只要想办法触发一次重启，限流窗口就归零了。

**仍存在**：`ConcurrencyGuard` 的并发计数保留在内存中。这是有意为之——进程重启后在途请求本就不存在，计数归零才是正确语义。

**因此必须单 worker 运行**：多进程会让 `GLOBAL_MAX_CONCURRENT` 实际变成 N 倍。网关启动时会用文件锁（`GATEWAY_DB.lock`）检测并拒绝第二个实例，误配置会直接报错退出，而不是静默失效。

### 4.2 无内容审核

服务对外生成内容，但链路上**没有任何内容过滤**。若被用于生成违法违规内容，责任在服务提供者。

**处理**：接入内容审核服务（云厂商的文本审核 API），在网关层做出口过滤；至少保留完整请求日志以便追溯。

### 4.3 请求审计日志（已解决）

已新增 `audit_log` 表，记录每次请求的来源 IP、Key、端点、状态码、结果类型、token 数、耗时与 User-Agent。

关键设计：**被拒绝的请求同样入库**。`auth_invalid`、`path_blocked`、`rate_limited`、`auth_flood` 这些恰恰是安全审计最关心的信号——只看成功请求的日志，等于把最有价值的线索丢掉了。

查询方式见 README 的「审计日志」一节。日常巡检用 `python cli.py audit --days 1 --summary` 看汇总即可，若 `auth_invalid` 或 `path_blocked` 突然增多，说明有人在扫描服务。

### 4.4 Key 分发渠道不可控

网关签发 Key 后，通过什么渠道给用户由你决定。明文发在群里、截图外传都会导致泄露。

**处理**：一对一私发；给每个用户单独签发，不要共用；定期用 `cli.py usage` 检查异常用量。

### 4.5 Cloudflare 侧未配速率限制

网关的限流要等请求到达进程才生效。在 Cloudflare 控制台再配一层 WAF 速率限制，可以在边缘就更早拦掉扫描和撞库。

**处理**：Cloudflare 控制台 → 安全性 → WAF → 速率限制规则，对 `/v1/*` 设置阈值。

### 4.6 依赖版本未锁定

`requirements.txt` 用的是 `>=`，重新部署可能装上不兼容或有已知漏洞的新版本。

**处理**：首次部署验证通过后执行 `pip freeze > requirements.lock`，生产环境按 lock 文件安装。

### 4.7 单点故障

网关是链路上的单点，它挂掉整条服务就断。

**处理**：systemd 配置 `Restart=always`（部署手册已含）；更高可用需多实例 + 负载均衡。

### 4.8 合规备案

按《生成式人工智能服务管理暂行办法》，面向**境内公众**提供生成式 AI 服务需完成算法备案与上线备案。

**处理**：小范围 Key 分发风险较低；对外开放注册前先确认备案要求。

### 关于 CLI 表格对齐（实现质量）

### 真实服务暴露的一个非安全问题：输出上限的设计

最初 `MAX_OUTPUT_TOKENS` 默认 4096，是一个拍脑袋的固定值。接入真实推理模型后暴露出两个问题，都已重新设计。

**问题一：固定上限对推理模型太紧。** 思维链的 `reasoning_tokens` 和正文共享 `max_tokens` 预算。实测同一复杂问题：

| 请求 max_tokens | 实际 completion | 其中思维链 | 正文字符数 |
|---|---|---|---|
| 64 | 64 | 64 | **0** |
| 256 | 256 | 256 | **0** |
| 1024 | 1024 | 134 | 1668 |
| 4096 | 4096 | 100 | 7803 |

预算偏小时正文为空，但返回 HTTP 200 + `finish_reason: length`。客户端不报错、日志显示成功、界面一片空白——极难定位。

**问题二：上游对超窗口取值的报错不可读。** 实测直连 SGLang：

| max_tokens | 结果 |
|---|---|
| 262144（= `max_model_len`） | ✅ 200 |
| 300000 | ❌ 400，**body 完全为空** |
| 1000000 | ❌ 400，body 空 |

客户端拿到一个没有任何说明的 400。顺带确认：SGLang 对「prompt + max_tokens 超窗口」自己会收敛（实测 4052 tokens prompt + `max_tokens=262144` 返回 200），只在 `max_tokens` 本身超过 `max_model_len` 时报错。

**重新设计：三级约束取最小值**

| 级别 | 来源 | 默认 |
|---|---|---|
| 1 | `MAX_OUTPUT_TOKENS` | `0`（不设人为上限） |
| 2 | 模型上下文窗口，启动时从 `/v1/models` 自动探测 | 自动 |
| 3 | 该 Key 当日剩余配额 | 自动 |

**验证**：

| 场景 | 结果 |
|---|---|
| 5M 配额，`max_tokens=300000` | 200，钳到窗口 262144，模型自然停止（6540 tokens） |
| 3K 配额，`max_tokens=100000` | 200，钳到剩余配额 **3000**，`finish=length` |
| 5M 配额，`max_tokens=8192` | 200，原样透传 |

第 1 行是重点：直连时是空 body 的 400，经网关变成正常响应。

**第三级（剩余配额）解决了另一个隐患**：配额校验在请求**开始前**做，原本一个 `max_tokens` 拉满的请求就能把当天额度打穿数倍。加这一级后单次请求不会超过剩余配额。

**顺带修的**：`daily_tokens <= 0` 原本会导致所有请求被拒（`used >= 0` 恒真），现在按「不限量」处理，与 `MAX_OUTPUT_TOKENS=0` 的约定一致。

**代价要说清楚**：放开上限后单次请求最长可跑约 24 分钟（262144 tokens ÷ 约 178 tok/s）。Cloudflare 免费版源站超时 100 秒不可调，长生成**必须走流式**；同时长请求会长时间占用并发位，需要盯住 `GLOBAL_MAX_CONCURRENT`。

**延迟参考**：生成 4096 tokens 约 23 秒，简单问题约 2 秒。
