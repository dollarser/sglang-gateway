# SGLang + Qwen 对外服务部署手册

面向**一台全新机器**的从零部署流程。按顺序执行即可，每一步都有验证方法。

- 目标形态：SGLang 部署 Qwen，通过 API Key 网关鉴权，再用 Cloudflare Tunnel 暴露到公网
- 适用平台：Linux 服务器（主）/ macOS（备）
- 预计耗时：模型下载占大头，其余约 30 分钟

---

## 一、架构总览

```
公网用户
   │  Authorization: Bearer sk-qw-xxxxx
   ▼
Cloudflare 边缘网络（免费 TLS、WAF、速率限制）
   │
   ▼
cloudflared 隧道（内网主动出站，无需公网 IP）
   │
   ▼
API Key 网关        127.0.0.1:2233
   ├─ 校验网关 Key（SHA-256 比对）
   ├─ 每分钟请求数限流（状态持久化，重启不清零）
   ├─ 每日 token 配额
   ├─ 单 Key 并发上限 + 全局并发闸门
   ├─ 请求兼容改写（developer 角色 / 参数别名 / 上下文溢出重试）
   ├─ 记录用量
   └─ 记录审计日志（含被拒绝的请求）
   │
   ▼
SGLang + Qwen       127.0.0.1:30007
```

三个组件都只监听回环地址，**唯一对外的出口是 cloudflared 建立的那条出站隧道**。

| 组件 | 端口 | 对外暴露 | 职责 |
|---|---|---|---|
| SGLang | 30007 | 否 | 推理服务 |
| API Key 网关 | 2233 | 否 | 鉴权、限流、计量、审计、兼容改写 |
| cloudflared | 出站 | 是（经隧道） | 打通公网 |

> **端口约定**：本手册统一用 `30007`（本机实际部署的端口）。SGLang 自身默认是 `30000`，
> 按你的实际情况调整即可，但**网关的 `SGLANG_BASE_URL` 必须与之一致**，否则全是 502。
>
> 网关和 SGLang 之间**不要**再插转发层。早期版本曾有一个独立的兼容代理（`30008 -> 30007`），
> 现已把兼容逻辑内化进网关（`sglang_compat.py`），链路由四跳减为三跳。

## 二、前置准备

### 2.1 硬件

按模型规模估算显存（含 KV Cache 余量，仅供参考）：

| 模型 | 精度 | 显存需求 |
|---|---|---|
| Qwen3-8B | BF16 | 约 20 GB |
| Qwen3-14B | BF16 | 约 32 GB |
| Qwen3-32B | BF16 | 约 68 GB |
| Qwen3-32B | FP8 | 约 36 GB |
| Qwen3-72B | BF16 | 约 150 GB |

显存不足时用 `--tp-size N` 做多卡张量并行，或选 FP8 / AWQ 量化版本。

### 2.2 软件与账号

| 项目 | 要求 |
|---|---|
| 操作系统 | Ubuntu 22.04+ / Debian 12+ / macOS 13+ |
| Python | 3.10 及以上 |
| GPU 驱动 | CUDA 12.1+（NVIDIA） |
| Cloudflare 账号 | 免费版即可 |
| 域名 | **必须已托管在 Cloudflare**（DNS 由 Cloudflare 管理） |

> 域名是关键前提。没有域名就只能用临时隧道，而临时隧道不支持流式输出。

### 2.3 需要迁移的文件

从旧机器带走网关项目：

```bash
# 旧机器上打包
cd ~
tar czf gateway.tar.gz gateway --exclude='__pycache__' --exclude='*.db' --exclude='*.db-wal' --exclude='*.db-shm' --exclude='*.lock'

# 传到新机器
scp gateway.tar.gz user@新机器IP:~/
```

> 排除 `*.db` 是有意的：新机器上重新签发 Key 更干净。但如果你想把现有用户和用量一起搬过去，就不要排除数据库，直接连 `gateway.db` 一起打包（搬完记得 `chmod 600`）。
>
> `*.lock` 一定要排除——那是单实例锁文件，带过去会干扰新机器上的启动判断。

## 三、部署 SGLang 与 Qwen

### 3.1 安装 SGLang

```bash
# 建议先建独立虚拟环境
python3 -m venv ~/sglang-env
source ~/sglang-env/bin/activate

pip install --upgrade pip
pip install "sglang[all]"
```

国内网络慢的话换源：

```bash
pip install "sglang[all]" -i https://pypi.tuna.tsinghua.edu.cn/simple
```

**备选：Docker 方式**（省去环境折腾）

```bash
docker run --gpus all --shm-size 32g -p 127.0.0.1:30007:30007 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  --ipc=host lmsysorg/sglang:latest \
  python3 -m sglang.launch_server \
    --model-path Qwen/Qwen3-32B \
    --host 0.0.0.0 --port 30007
```

注意 Docker 方式下容器内要监听 `0.0.0.0`，但**宿主机端口映射必须限定为 `127.0.0.1:30007:30007`**，这样外部仍然访问不到。

### 3.2 下载模型

国内推荐用 ModelScope，速度稳定：

```bash
pip install modelscope
modelscope download --model Qwen/Qwen3-32B --local_dir ~/models/Qwen3-32B
```

或者用 HuggingFace（需要网络条件）：

```bash
pip install huggingface_hub
huggingface-cli download Qwen/Qwen3-32B --local-dir ~/models/Qwen3-32B
```

### 3.3 启动推理服务

```bash
source ~/sglang-env/bin/activate

python -m sglang.launch_server \
  --model-path ~/models/Qwen3-32B \
  --served-model-name qwen \
  --host 127.0.0.1 \
  --port 30007 \
  --api-key "换成你自己的后端密钥" \
  --tp-size 1 \
  --context-length 32768 \
  --mem-fraction-static 0.85
```

关键参数说明：

| 参数 | 作用 |
|---|---|
| `--host 127.0.0.1` | **必须**。只监听回环，杜绝外部直连 |
| `--served-model-name qwen` | 客户端填的模型名，起个短的好记 |
| `--api-key` | 后端密钥，网关用它访问 SGLang。用户永远接触不到 |
| `--tp-size` | 张量并行卡数，单卡填 1 |
| `--context-length` | 上下文长度，越大占显存越多 |
| `--mem-fraction-static` | 静态显存占比，显存紧张时调低 |

> 如果你的 SGLang 版本不支持 `--api-key` 参数，去掉它即可，网关侧对应地不配 `SGLANG_API_KEY` 环境变量。此时 SGLang 只靠「仅监听回环」这一层保护，仍然安全。

### 3.4 验证

```bash
curl http://127.0.0.1:30007/v1/models \
  -H "Authorization: Bearer 换成你自己的后端密钥"
```

返回模型列表即成功。同时确认外部访问不通：

```bash
curl http://新机器公网IP:30007/v1/models   # 应当连接失败
```

## 四、部署 API Key 网关

### 4.1 解压项目

```bash
tar xzf ~/gateway.tar.gz -C ~/
cd ~/gateway
ls    # 应看到 app.py store.py cli.py run.sh requirements.txt README.md
```

### 4.2 安装依赖

网关的依赖很轻，单独建一个环境：

```bash
python3 -m venv ~/gateway-env
source ~/gateway-env/bin/activate
pip install -r requirements.txt
```

### 4.3 配置环境变量

**推荐做法：直接改 `run.sh` 头部的配置区。** 端口、后端地址、并发上限都在那里，改完 `./run.sh` 就能跑，比每次敲一长串 export 可靠。

```bash
cd ~/gateway
vi run.sh     # 改开头的「配置区」
./run.sh
```

如果要用 systemd 托管，环境变量写进 service 文件（见 6.7 节）。

各参数的含义与取值建议：

| 变量 | 说明 |
|---|---|
| `SGLANG_BASE_URL` | SGLang 地址，保持回环。**填裸 SGLang 的端口**（兼容改写已内化进网关，不要再填代理端口） |
| `SGLANG_API_KEY` | 与 SGLang 的 `--api-key` 一致，网关自动附加到上游请求 |
| `GATEWAY_DB` | 数据库路径，**必须绝对路径**。写成相对路径会静默新建空库，表现为所有 Key 突然失效 |
| `GLOBAL_MAX_CONCURRENT` | 全局在途请求上限，**建议 16**（默认 32 偏高），见 README 的实测数据 |
| `MAX_OUTPUT_TOKENS` | 单次输出上限，默认 `0` = 不限制。由上下文窗口 + 剩余配额兜底，见 4.6 |
| `MODEL_MAX_LEN` | 模型上下文窗口，默认 `0` = 启动时自动探测。探测失败时手工指定 |
| `COMPAT_REWRITE` | 是否做请求兼容改写（`developer` 角色折叠、参数别名），默认 `1` |
| `COMPAT_CONTEXT_RETRY` | 上下文溢出时是否自动降 `max_tokens` 重试一次，默认 `1` |
| `CONTEXT_RETRY_SAFETY_TOKENS` | 重试时的安全边距，默认 `512` |
| `AUTH_FAIL_MAX` | 单 IP 每分钟鉴权失败上限，默认 20 |
| `CHARS_PER_TOKEN` | usage 缺失时的兜底折算系数，默认 2.0（中文场景偏保守） |
| `SINGLETON_LOCK` | 单实例锁文件，默认 `<GATEWAY_DB>.lock`，一般不用改 |
| `INJECT_STREAM_USAGE` | 流式请求自动注入 `stream_options`，让用量统计精确 |
| `CORS_ORIGINS` | 若给网页端调用，改成具体域名更安全 |

完整的参数分析与实测数据见 `README.md` 的「参数是否要调」一节。

### 4.4 输出长度：不设人为上限

网关默认 `MAX_OUTPUT_TOKENS=0`（不限制），改用**三级约束取最小值**：

| 级别 | 来源 | 作用 |
|---|---|---|
| 1 | `MAX_OUTPUT_TOKENS` | 需要硬上限时才用，默认不设 |
| 2 | **模型上下文窗口**（启动时自动探测） | 把超窗口的取值钳到合法范围 |
| 3 | **该 Key 当日剩余配额** | 单次请求不会把当天额度打穿 |

**为什么必须探测上下文窗口**：上游对 `max_tokens > max_model_len` 的请求会直接返回 400。实测直连裸 SGLang：

| 直连 SGLang，max_tokens= | 结果 |
|---|---|
| 262144（= `max_model_len`） | ✅ 200 |
| 300000 | ❌ 400 `max_completion_tokens is too large: 300000. This model supports at most 262144 completion tokens.` |

客户端拿到的是 400，多数 SDK 会把 `message` 弹给用户。网关把超出的值钳到窗口大小后，同样的请求正常返回内容。启动日志里能看到探测结果：

```
INFO [gateway] 输出长度上限：MAX_OUTPUT_TOKENS=不限，模型上下文窗口=262144
```

> 探测失败（网关比 SGLang 先启动）不致命，只是不做窗口钳制，日志会提示。可以显式设置 `MODEL_MAX_LEN=262144`。

**为什么还要配额钳制**：配额在请求**开始前**校验，一个 `max_tokens` 拉满的请求就能把当天额度打穿好几倍。实测 3K 配额的 Key 请求 `max_tokens=100000`，被钳到 3000。

**推理模型的注意点**：思维链的 `reasoning_tokens` 和正文共享 `max_tokens` 预算。实测同一个复杂问题：

| 请求 max_tokens | 实际 completion | 其中思维链 | 正文字符数 |
|---|---|---|---|
| 64 | 64 | 64 | **0** |
| 256 | 256 | 256 | **0** |
| 1024 | 1024 | 134 | 1668 |
| 4096 | 4096 | 100 | 7803 |

预算太小的时候正文为空，但返回 HTTP 200 + `finish_reason: length`——客户端不报错、日志显示成功、界面一片空白。放开上限后这个问题自动消失，但要注意：**`max_tokens` 是客户端传的**，如果用户客户端的默认值偏小（常见 2048/4096），网关替不了。

**延迟与并发的代价**：实测生成 4096 tokens 约 23 秒，简单问题约 2 秒。放开上限后单次请求最长可跑约 **24 分钟**（262144 tokens ÷ 约 178 tok/s）。两个后果：

- Cloudflare 免费版源站超时 100 秒且不可调 → 长生成**必须走流式**，否则 524
- 长请求长时间占用并发位 → 4 个用户各开 4 路就能占满 `GLOBAL_MAX_CONCURRENT=16`

如果发现长请求影响其他人，回到 `MAX_OUTPUT_TOKENS=32768`（约 3 分钟）之类的中间值。

### 4.5 签发第一个密钥

```bash

source ~/gateway-env/bin/activate

```

输出里的**密钥只显示这一次**，立刻保存。这就是发给用户的 `sk-qw-...`。

### 4.6 启动并验证

```bash

```

脚本会先把当前配置打印出来，确认「SGLang 后端」「监听」「数据库」三项都对：



## 六、创建与配置 Tunnel

这一节是核心。**注意：本机可能已有一个正在运行的 Tunnel（`cloudflared tunnel list` 能看到）**，那是别的用途的，不要动它。

> 「不要复用」指的是**别复用别的用途的隧道**。如果你是把**同一套服务**从旧机器搬到新机器，复用原来那条隧道反而更好（DNS 零改动）——见 6.8。

> 第一次操作、想要手把手的版本（每一步的命令、预期输出、怎么验证、常见报错对照），见《Cloudflare-Tunnel-创建与域名绑定.md》。本节只列要点。

### 6.1 登录 Cloudflare

```bash
cloudflared tunnel login
```

会自动打开浏览器，选择要授权的域名。成功后生成 `~/.cloudflared/cert.pem`。

无图形界面的服务器上，它会打印一个 URL，把 URL 复制到本地浏览器打开完成授权即可。

### 6.2 创建 Tunnel

```bash
cloudflared tunnel create sglang-gateway
```

输出里会有 Tunnel ID（一串 UUID），并生成凭证文件：

```
~/.cloudflared/<TUNNEL_ID>.json
```

**记下这个 TUNNEL_ID**，下一步要用。

### 6.3 绑定域名

```bash
cloudflared tunnel route dns sglang-gateway llm.example.com
```

把 `llm.example.com` 换成你自己的域名。这条命令会自动在 Cloudflare 创建一条指向隧道的 CNAME 记录。

### 6.4 编写 config.yml

创建 `~/.cloudflared/config.yml`：

```yaml
tunnel: <TUNNEL_ID>
credentials-file: /home/你的用户名/.cloudflared/<TUNNEL_ID>.json

ingress:
  - hostname: llm.example.com
    service: http://127.0.0.1:2233
  - service: http_status:404
```

三个要点：

1. `service` 指向**网关的 2233**，不是 SGLang 的 30007
2. `credentials-file` 必须写**绝对路径**
3. **最后一条兜底规则 `http_status:404` 不能少**，否则未匹配的请求会被转发到错误的服务

校验配置：

```bash
cloudflared tunnel ingress validate
```

### 6.5 前台试运行

先在前台跑一次，确认没问题再装服务：

```bash
cloudflared tunnel run sglang-gateway
```

看到 `Registered tunnel connection` 就是连上了。另开终端测试公网访问：

```bash
curl https://llm.example.com/v1/models \
  -H "Authorization: Bearer sk-qw-你的密钥"
```

返回模型列表即打通。

### 6.6 安装为后台服务

确认无误后 `Ctrl+C` 停掉前台进程，装成系统服务。

**Linux（systemd）：**

```bash
sudo cloudflared service install
sudo systemctl enable cloudflared
sudo systemctl start cloudflared
sudo systemctl status cloudflared
```

它会读取 `~/.cloudflared/config.yml`。注意：`sudo` 安装后服务以 root 运行，配置文件路径需要是 root 能访问的绝对路径。

**macOS（launchd）：**

```bash
cloudflared service install
```

macOS 上这会装成**用户级 launch agent**，不需要 sudo。不带 token 参数时，它会读取 `~/.cloudflared/config.yml`。

### 6.7 让三个组件都开机自启

cloudflared 已经处理好了。SGLang 和网关也需要自启，以 Linux 为例：

`/etc/systemd/system/sglang.service`：

```ini
[Unit]
Description=SGLang Qwen Server
After=network.target

[Service]
Type=simple
User=你的用户名
WorkingDirectory=/home/你的用户名
Environment="PATH=/home/你的用户名/sglang-env/bin:/usr/local/bin:/usr/bin"
ExecStart=/home/你的用户名/sglang-env/bin/python -m sglang.launch_server \
  --model-path /home/你的用户名/models/Qwen3-32B \
  --served-model-name qwen \
  --host 127.0.0.1 --port 30007 \
  --api-key 换成你自己的后端密钥
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

`/etc/systemd/system/sglang-gateway.service`：

```ini
[Unit]
Description=SGLang API Key Gateway
After=network.target sglang.service

[Service]
Type=simple
User=你的用户名
WorkingDirectory=/home/你的用户名/gateway
Environment="SGLANG_BASE_URL=http://127.0.0.1:30007"
Environment="SGLANG_API_KEY=换成你自己的后端密钥"
Environment="GATEWAY_DB=/home/你的用户名/gateway/gateway.db"
Environment="GLOBAL_MAX_CONCURRENT=32"
Environment="PATH=/home/你的用户名/gateway-env/bin:/usr/local/bin:/usr/bin"
# 绝对不要加 --workers 参数，本网关必须单进程运行，原因见下方说明
ExecStart=/home/你的用户名/gateway-env/bin/uvicorn app:app --host 127.0.0.1 --port 2233
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

> **关于单 worker**
>
> 网关**必须单进程运行**，不要加 `uvicorn --workers N`。原因：限流状态虽然已经持久化到 SQLite，但**并发计数仍在内存里**，多进程会让 `GLOBAL_MAX_CONCURRENT` 实际变成 N 倍，全局并发闸门形同虚设。
>
> 网关启动时会用文件锁（`GATEWAY_DB.lock`）检测这种情况——如果同一个数据库已经被另一个进程使用，第二个实例会**直接报错退出**，而不是静默地让限制失效。所以误加 `--workers` 时你会立刻看到启动失败，不会埋下隐患。
>
> 单进程处理 LLM 这种 IO 密集型场景完全够用：瓶颈在 GPU，不在网关。

启用：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now sglang sglang-gateway
```

**启动顺序很重要**：SGLang 加载模型要几分钟，网关启动时会连不上上游，但因为设置了 `Restart=always`，它会自己重试，不用管。

### 6.8 迁移场景：换机器，域名不变

上面 6.1–6.3 讲的是「从零建隧道」。如果你只是把**同一套服务**搬到另一台机器，域名**不用改、也不用重新申请**——域名绑的是**隧道 UUID**，不是机器的 IP。

四层归属，一眼看清换机器动了什么：

| 层 | 内容 | 住在哪 |
|---|---|---|
| 域名 | `llm.example.com` | Cloudflare 账号 |
| DNS | `CNAME → <TUNNEL_ID>.cfargotunnel.com` | Cloudflare 账号 |
| 隧道对象 | `sglang-gateway` | Cloudflare 账号 |
| **connector** | `cloudflared` 进程 → `http://127.0.0.1:2233` | **某台机器** |

只有最下面那层跟机器绑定。所以换机器、换网络、换公网 IP，域名一律照旧——这正是隧道比「DDNS + 端口映射」省心的地方。

#### 方式 A：复用同一条隧道（DNS 零改动）

```bash
# 1) 旧机器：先停掉 connector —— 不能跳过，原因见下方「四个坑」第 1 条
pkill -f "run sglang-gateway"

# 2) 只拷这两个文件到新机器
scp ~/.cloudflared/<TUNNEL_ID>.json  新机器:~/.cloudflared/
scp ~/.cloudflared/config.yml        新机器:~/.cloudflared/

# 3) 新机器：改 config.yml 里的 credentials-file 路径（绝对路径，见「四个坑」第 2 条）

# 4) 新机器起隧道
cloudflared tunnel --no-autoupdate run sglang-gateway
```

**不需要 `cert.pem`。** 它只用于 `tunnel create` / `route dns` 这类管理操作，运行时用不到。少传一个账号级凭证，攻击面更小。

验证 connector 只剩新机器：

```bash
cloudflared tunnel info sglang-gateway
```

#### 方式 B：新建隧道 + 覆盖 CNAME

```bash
cloudflared tunnel login                              # 授权同一个域名
cloudflared tunnel create sglang-gateway-2            # 拿到新 UUID；别用同名，同名会提示已存在
cloudflared tunnel route dns -f sglang-gateway-2 llm.example.com
```

`-f`（`--overwrite-dns`）会把已存在的 CNAME 直接覆盖成指向新隧道，覆盖那一刻旧隧道就收不到流量了。

**怎么选：**

| | 方式 A 复用 | 方式 B 新建 |
|---|---|---|
| DNS 改动 | 无 | 覆盖 CNAME |
| 需要 `cert.pem` | 否 | 是（要 `tunnel login`） |
| 切换是否平滑 | **否**，必须先停旧机器 | 是，覆盖即切 |
| 适合 | 临时借用另一台机器 | 永久迁移 |
| 旧隧道善后 | 留着即可 | 记得 `cloudflared tunnel delete`，否则 CNAME 悬空 |

#### 四个坑

1. **同一条隧道的多个 connector 是负载均衡，不是主备。** 两台机器都跑着、只有一台有源站 → 请求随机一半打到空源站，表现是**时好时坏的 502**。所以方式 A 必须先停旧机器，别想着「先起新的再停旧的」平滑切换。
2. **`config.yml` 里的 `credentials-file` 是绝对路径**（见 6.4 第 2 点）。新机器用户名不同就必须改，否则起不来。`ingress` 也要确认指向本机 `http://127.0.0.1:2233`。
3. **凭证分两级，别一起打包传。** `<TUNNEL_ID>.json` 是隧道级（泄露 = 别人能往你的隧道挂源站）；`cert.pem` 是账号级（能建/删隧道、改 DNS，权限大得多）。走 `scp`，别过聊天工具或公开仓库。旧机器转手或报废前，清掉 `~/.cloudflared/`。
4. **`metrics` 端口冲突。** `config.yml` 里的 `metrics: 127.0.0.1:20242` 在新机器上若被占用，错开一个。

> 本机实际使用的隧道名、Tunnel ID、域名，以及可直接照抄的命令，见《Tunnel-上线记录与运维.md》第七节（该文件含真实值，未纳入公开仓库）。

## 八、日常运维

```bash
cd ~/gateway && source ~/gateway-env/bin/activate
export GATEWAY_DB=/home/你的用户名/gateway/gateway.db

# 签发新密钥
python cli.py create --name bob --rpm 120 --daily-tokens 5000000 --max-concurrent 8

# 查看所有密钥
python cli.py list

# 吊销
python cli.py revoke bob

# 看用量
python cli.py usage --days 7

# 看审计汇总（日常巡检看这一条就够）
python cli.py audit --days 1 --summary

# 查可疑行为
python cli.py audit --days 7 --outcome auth_invalid      # 有人在撞 Key
python cli.py audit --days 7 --outcome path_blocked      # 有人在扫路径
python cli.py audit --days 7 --ip 1.2.3.4                # 某个 IP 都干了什么

# 清理历史记录与限流事件
python cli.py cleanup --keep-days 30
```

### 8.1 审计日志看什么

每次请求都会落一条记录，**被拒绝的请求也在内**。日常巡检只需关注 `--summary` 的输出：

```
结果                    次数      最近一次
--------------------------------------------------------
ok                      1240      2026-09-29 11:08:34
rate_limited            83        2026-09-29 11:07:12
auth_invalid            2         2026-09-29 11:06:40
path_blocked            1         2026-09-29 11:05:55
```

几个判断规则：

| 现象 | 含义 | 处理 |
|---|---|---|
| `auth_invalid` 持续增长 | 有人在用垃圾 Key 撞库 | 确认 `AUTH_FAIL_MAX` 生效，必要时在 Cloudflare 侧加规则 |
| `path_blocked` 出现 | 有人在探测管理端点 | 正常防护已拦住，记录下来即可 |
| `auth_flood` 出现 | 某个 IP 已被暂时封禁 | 看 `--ip` 明细确认是否误伤 |
| `client_abort` 频繁 | 客户端 bug 或有人抓一半就走 | 按 IP 排查，注意这类请求**照常计费** |
| `service_busy` 增多 | 全局并发已满 | 要么调大 `GLOBAL_MAX_CONCURRENT`，要么排查是否有用户开太多并发 |
| `upstream_unreachable` | SGLang 挂了或地址配错 | 查 `systemctl status sglang` |

`client_abort` 的状态码记作 **499**（nginx 对「客户端提前关闭连接」的约定），所以在明细里一眼就能和正常完成的 200 区分开。

### 8.2 单实例约束

网关**必须单进程运行**，不要加 `uvicorn --workers N`。它启动时会对 `GATEWAY_DB.lock` 加排他锁：

```bash
cat ~/gateway/gateway.db.lock    # 输出当前网关进程的 PID
```

如果误启动第二个实例，它会**直接报错退出**：

```
RuntimeError: 另一个网关实例正在使用 /home/.../gateway.db（锁文件 .../gateway.db.lock）。
本网关设计为单 worker 运行，请先停掉已有实例。
```

这是有意设计。多实例不会报错，但会让全局并发上限静默翻倍，排查成本远高于直接启动失败。

调整已有 Key 的配额目前需要直接改数据库：

```bash
sqlite3 $GATEWAY_DB "UPDATE api_keys SET daily_tokens = 10000000 WHERE name = 'bob';"
```

## 九、故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 公网返回 404 | 客户端 base_url 的 `/v1` 后缀不对 | 去掉或补上 `/v1` 再试 |
| 公网返回 401 | 地址对了，Key 有问题 | 检查是否用了 SGLang 的后端密钥而非网关密钥 |
| 公网返回 502 | 网关连不上 SGLang | 确认 SGLang 在跑、端口对、`SGLANG_BASE_URL` 正确 |
| 公网返回 524 | Cloudflare 100 秒源站超时 | 多为首 token 太慢，检查显存是否吃紧、context 是否过长 |
| 流式变成一次性返回 | 中间层开了缓冲 | 确认网关是直连 SGLang，没有额外 Nginx 加了 `proxy_buffering on` |
| 502 且日志有 `credentials-file` 报错 | config.yml 路径写成了相对路径 | 改成绝对路径 |
| Tunnel 连不上 | 出站被防火墙拦 | 确认能访问 7844 端口 |
| 公网**时好时坏**的 502 | 同一条隧道在两台机器上都有 connector，流量被负载均衡到没源站的那台 | `cloudflared tunnel info <隧道名>` 看 connector 列表，停掉多余的那个，见 6.8 |
| 换机器后隧道起不来，日志报 `credentials-file` | `config.yml` 里写的是旧机器的绝对路径 | 改成新机器的路径，见 6.8 |
| 服务启动后立刻退出 | 环境变量没传进 systemd | 检查 `Environment=` 是否漏了 `GATEWAY_DB` 的绝对路径 |
| 启动报「另一个网关实例正在使用…」 | 已有实例在跑，或误加了 `--workers` | 先停掉旧实例；确认 `ExecStart` 里没有 `--workers` |
| 用量统计为 0 | 上游没返回 usage | 确认 `INJECT_STREAM_USAGE=1` |
| 返回 200 但正文空白 | **推理模型的思维链吃光了 `max_tokens`** | 调高 `MAX_OUTPUT_TOKENS`（不低于 2048），见 4.4 |
| 公网返回 524 | 生成太长撞上 Cloudflare 100 秒超时 | 让客户端走流式，或降低 `MAX_OUTPUT_TOKENS` |
| 重启后限流没重置 | 正常行为 | 限流状态持久化在 `rate_events` 表，重启不清零是设计意图 |
| 审计日志表越来越大 | 未做清理 | 加个 cron 定期跑 `cli.py cleanup --keep-days 30` |

查看日志：

```bash
sudo journalctl -u sglang -f
sudo journalctl -u sglang-gateway -f
sudo journalctl -u cloudflared -f
```

网关进程的日志只含错误和拦截告警；**请求级的完整记录在审计表里**，用 `cli.py audit` 查。
